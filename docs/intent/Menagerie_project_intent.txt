4. Dual-Seed Data Architecture
To prevent memory leaks in infinite scaling and ensure complete data integrity across saved files, every creature, player item, and world object uses a unified dual-seed data model.
      [ UNIQUE OBJECT DATA PAYLOAD ]
        /                        \
       v                          v
[ InitialSeed ]            [ MutationSeed ]
  - Immutable                - Mutable / Dynamic
  - Deterministic DNA        - Tracks Permanent Boosts

4.1 Creature Seed Architecture
InitialSeed (String/Hash): The unique immutable hash generated at the exact millisecond of a creature's initial instantiation. It acts as the creature's underlying DNA, dictating its base hidden stats, base weight/size variations, and secret passive ability unlocks.
MutationSeed (String/Hash): A mutable hash that maps changes whenever a creature undergoes a permanent stat alteration. This includes training tower loops, reincarnation prestige points, or initial stat overrides via capture upgrades.
4.2 Item Seed Architecture
InitialSeed (String/Hash): A standardized, immutable hash shared by all identical items belonging to the same base blueprint or archetype. It ensures structural uniformity upon initial craft or drop.
ModificationSeed (String/Hash): A dynamic, evolutionary hash string that alters its data state whenever a player adds stats via item refinement, prototyping towers, or ingredient infusion.
4.3 Environmental & Dimensional Seeds
Dungeon towers and overworld zones read seed strings directly to construct their layout grids. When a player runs an item through a Prototyping Tower, the item’s InitialSeed and ModificationSeed combine to generate a unique layout.

5.3 Infinite Scaling Mathematical Models
The game completely eliminates level caps and stat caps. To prevent calculations from overflowing the standard 64-bit float limits while maintaining a perceptible sensation of progression, all core parameters scale using a linear-log hybrid algorithm.
Stat Growth Formula
The calculation of an active stat $S$ at level $L$ uses the following function:
$$S(L) = S_{\text{base}} \times \left(1 + \alpha L + \beta \ln(L + 1)\right) \times \prod M_{\text{seed}}$$
Where:
$S_{\text{base}}$ is the baseline species attribute.
$\alpha$ is the linear scaling growth coefficient ($\alpha \approx 0.05$).
$\beta$ is the logarithmic balancing coefficient ($\beta \approx 12.5$).
$M_{\text{seed}}$ represents the compound product of all hidden seed values and shiny multipliers.
Experience Calculation Formula
The experience points required to advance from Level $L$ to $L+1$ follow an exponential curve:
$$E(L) = \lfloor \gamma \times L^{1.5} \times \ln(L + 2) \rfloor$$
Where $\gamma$ is the global experience pace constant.

14.1 The Man-at-Arms NPC Handler
Building an Arena automatically instantiates a persistent Man-at-Arms NPC entity. This character serves as the primary interface anchor for all competitive features, wager tracking, and leaderboard match reviews.
14.2 Daily Simulated Wagering Loop
The system runs daily automated NPC battles within the Arena structure. These fights simulate combat using pure AI scripts, allowing players to research creature matchups, study move configurations, and wager in-game currency on the results. Winning wagers yield specialized resources and arena points used to acquire unique Arena Gear sets.
14.3 Asynchronous PvP Ladder Leagues
True 1v1 Combat Simulations: The leaderboard does not rely on arbitrary score tracking. Rankings are determined by actual 1v1 combat simulations processed on the backend, checking creature stats, passive layouts, and ability arrays directly against each other.
Dynamic Arenas & Rule Modifiers: Leagues are divided into tiered brackets. Each bracket features unique battlefield layouts, environmental traps, and distinct tile hazards that match various element or class combinations.
Match Replay System: All leaderboard matches are recorded by the simulation backend as structural command streams. This allows players to review match replays, study team compositions, analyze positioning behavior, and optimize their defensive setups.

17. System Architecture Verification
To guarantee that Menagerie remains completely stable under intensive processing conditions, the platform's core code architecture uses specific structural validations:
17.1 Memory Allocation & Serialization Limits
Procedural Garbage Collection: Overworld chunks are dynamically unloaded from active volatile memory (RAM) whenever the player moves more than 3 chunk radii away from them. Their updated states are serialized into localized delta files (.diff) to prevent memory consumption from growing indefinitely during exploration.
Numeric Overflow Protection: All primary math operators for calculations beyond Level 10,000 are evaluated via logarithmic scales. This prevents unexpected application crashes or execution errors if damage calculations cross into extremely high numbers.
17.2 Pathfinding Optimization Constraints
Hierarchical Pathfinding (HPA):* To keep frame rates stable across massive open areas or broad 3-unit dungeon hallways, pathfinding calculations are broken down into localized macro-grids before validating exact tile paths. This isolates pathfinding updates and keeps processing overhead clean during large-scale group encounters.
